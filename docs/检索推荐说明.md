# 检索 / 推荐技术方案（图 → 属性 → 整身穿搭相似检索）

> **定位**：把主线 demo（图 → 结构化属性 JSON）的终点变成起点——用抽出的 18 维属性 + 视觉特征，在 DeepFashion-MultiModal 全库（约 4.4 万张图 / **12,908 套穿搭**）里检索最相似的「**整套穿搭**」，让 demo 升级成「图 → 属性 → 相似穿搭检索」完整场景。
>
> **实现**：**属性 + 视觉向量混合检索**，**以「一套穿搭」为检索单位**。用冻结的 Qwen3-VL 视觉塔（`model.visual`）抽库内图 embedding 走向量检索，叠加官方标注的属性约束做加权；检索按 `(id, 子序号)` 聚合成套，展示细化到每个角度。

---

## 1. 方案概述

相似度由**两类信号 + 一种聚合**决定：

| 维度 | 来源 | 作用 |
|---|---|---|
| 视觉特征 | 冻结 Qwen3-VL 视觉塔抽库内图 embedding | 视觉形态相似 |
| 属性语义 | 查询 JSON 与库内官方属性真值匹配 | 语义可控（面料/图案/款式） |
| 按套聚合 | `(id, 子序号)` 一组，组内取最高分角度 | 检索单位是一"套穿搭"，而非单张图 |

复用现有 `model.visual` 与现有数据，零新增标注、不动训练；检索结果可信、可复用，且天然能做「官方标注 vs 模型抽取」的可视对照。

## 2. 数据基础（全部现成，零新增标注）

| 数据 | 位置 | 用途 |
|---|---|---|
| 图片 44,096 张 | `data/data_convert/deepfashion_multi/images/` | 抽视觉 embedding 的图库 |
| 形状标注 `shape_anno_all.txt` | `.../labels/shape/shape_anno_all.txt` | 12 维形状属性 id（检索约束，官方真值） |
| 纹理标注 `fabric_ann.txt` / `pattern_ann.txt` | `.../labels/texture/` | 上/下/外装面料 + 图案 id |
| 文本描述 `captions.json` | `data/data_convert/deepfashion_multi/` | 展示用 caption |
| 属性表 `SHAPE_ATTRS` / `FABRIC_VALS` / `PATTERN_VALS` | `scripts/data_convert_deepfashion_multi.py` | id → 语义映射 |

**关键点**：索引用**官方标注**（真值）而非模型抽取结果做检索约束，检索结果可信、可复用。

### 2.1 图片命名规则（实测统计）

文件名格式：

```
<大类>-<小类>-id_<商品id>-<子序号>_<视角号>_<角度>.jpg
```

| 字段 | 取值 | 实测说明 |
|---|---|---|
| 大类 | `WOMEN` / `MEN` | 男装 5,437 / 女装 38,659 张 |
| 小类 | 17 种 | `Denim / Tees_Tanks / Blouses_Shirts / Dresses / Skirts / Pants / Jackets_* / Cardigans / Suiting / Rompers_Jumpsuits / Leggings / Shorts / Sweaters / Sweatshirts_Hoodies / Graphic_Tees / Shirts_Polos` 等 |
| **商品 id** | 8 位数字 | **一个 id = 一个款**，全库 **7,975** 个唯一 id |
| **子序号** | 2 位 | **同款下的多个变体**（通常即不同颜色/花色），全库按 `(id,子序号)` 组合共 **12,908** 个 |
| 视角号 | 1 位 | **与角度完全固定配对**（见下表） |
| 角度 | 6 种 | 视角朝向 |

**视角号 ↔ 角度 是一对一固定配对**（实测，不会错配）：

| 视角号 | 角度 | 张数 |
|---|---|---|
| 1 | `front` | 12,421 |
| 2 | `side` | 8,805 |
| 3 | `back` | 8,377 |
| 4 | `full` | 6,471 |
| 6 | `flat` | 69 |
| 7 | `additional` | 7,953 |

**语义**：`front/side/back` 标准三视角、`full` 整身模特图、`flat` 平铺图（不穿人，69 张）、`additional` 补充/额外展示图。

> ⚠ **角度名不可全信**：`front` 可能是全身、`additional` 可能是正面（已在数据中观察到反例）。角度名只用来区分"同一款的哪张图"，**不代表真实拍摄朝向**。

### 2.2 检索单位：一套穿搭 = `(id, 子序号)`

- **商品 id** = 款（全库 7,975 个），**子序号** = 款下变体（通常即不同颜色/花色）；二者组合 `(id, 子序号)` 即**一套穿搭**——同款同色的不同**角度图**归为一组，全库共 **12,908** 套。
- **按套聚合为什么合理**：同一 `(id,子序号)` 内的多张图**穿法基本一致**（同款同色即同一穿法），差异仅在装饰品（配饰/小件）或某个角度展示的衣物细节更全。检索关心的是"穿法"，故把同一套的多角度归并、组内取最高分角度为代表（实现见 §3.3）。

## 3. 检索管线

```
用户上传图 ──▶ 属性抽取 demo（已有）──▶ 18 维属性 JSON
                                        │
                                        ▼
      ┌──────────────────────────────────────────────┐
      │  retrieval.py                                 │
      │  1. 视觉相似：查询图 embedding 与全库向量余弦     │
      │  2. 属性加权：查询 JSON 与官方属性命中率          │
      │  3. 按套聚合：(id,子序号) 一组，组内最高分为代表   │
      └──────────────────────────────────────────────┘
                                        │  top-k 套
                                        ▼
                         Gradio：套缩略图 → 点套看各角度 → 点角度看详情
```

### 3.1 视觉向量索引（离线，`build_retrieval_index.py`）

- 用**冻结的视觉塔**（`Qwen3-VL-8B-Instruct`，`model.visual`）对每张图抽 patch 特征。
- `vis(pixel_values, grid_thw=thw)` 返回 `.last_hidden_state`，形状 `[num_patches, 1152]`；`mean(dim=0)` 得 1152 维向量。
- 统一预处理：`image_processor.min_pixels=1024, max_pixels=825750`（与训练一致，不压缩细节）。
- **全量构建，不做角度预过滤**：全库 44,096 图**每图一条**，含 `id / sub / view / angle / image / attrs / caption`；
  - `index_vectors.npy` = (44,096 × 1152)（float32，约 203 MB）；
  - `index_meta.json` = 44,096 条（一个 list）；
  - 无任何 shape/caption 标注的图（`00001283 / 00003020 / 00004485` 共 9 张）**仍会进索引**（attrs 由 fabric/pattern 填充，仅 shape/caption 缺失），不会被过滤。
- 是否屏蔽某类角度（如 `side/back`）**不建索引时决定，而是挪到检索侧开关**（`retrieval.py --exclude-side-back / --angles`），换策略无需重抽索引。
- **多卡并行**：`--shard N --nshards M` 分片并行（每卡一段），`--merge` 合并为最终索引（本机已用 3×4090 构建全量，3 张卡并行，约 15 分钟）。

### 3.2 属性约束（真值加权）

- 查询 JSON 中**可见**的键值（模型已剔除不可见项），与库内官方 `shape+fabric+pattern` 属性比较。
- 属性匹配分 `attr_score = 命中维度数 / 查询总维度数`，作为**软加权**：

```
final = w_vis * vis_cos + w_attr * attr_score
默认 w_vis = 0.7, w_attr = 0.3
```

- 亦可对属性分 < 阈值（如 0.5）的候选做**硬过滤**（`--min-attr`）。

### 3.3 按套聚合（实现）

- 全库按 `(id, 子序号)` 聚合成套；**组内任意一个角度命中即可**，组得分 = **组内最高分那个角度**。
- `search(..., group=True)` 返回每套：`best_*`（该套最佳角度的缩略信息）+ `angles`（该套全部角度，按分数降序）。
- `group=False` 退化回每张图一条（兼容旧行为）。
- **同款不同颜色（不同子序号）= 不同套，分别保留**；同一套内的多角度**只在套内合并**（预览时逐个展示）。

## 4. 检索实现细节

### 4.1 优化策略（三件事）

检索的慢，主要卡在"抽查询图视觉向量"要用完整模型（8.8B / 17GB）。我们做了三件事把这块压下来：

| 策略 | 做了什么 | 解决什么 |
|---|---|---|
| **① 只加载视觉塔** | 用 `Qwen3VLVisionModel` 单独加载视觉塔（576M / 1.2GB），跳过 8B 语言模型（17GB） | 模型加载量大、慢 |
| **② 块级单例缓存** | `embed_query` 用模块级单例缓存视觉塔，只加载一次，之后复用 | 每次检索重复加载 |
| **③ 启动预热** | `serve_gradio.py` 启动时后台 `preload_vision_tower()` | 用户首次点击还要等加载 |

检索时视觉塔**只加载一次**（单例 `_query_model` 复用），之后不再加载；预热把这次加载挪到启动阶段，用户点击时视觉塔已在显存。三档方案的差别只在"视觉模型怎么就绪"：

- **基准A（原本）**：整模型冷加载抽视觉 ＋ 属性抽取(vLLM) ＋ 检索；
- **基准B（视觉塔冷）**：视觉塔冷加载抽视觉 ＋ 属性抽取(vLLM) ＋ 检索；
- **优化后（视觉塔＋预热）**：视觉塔已预热，点击只做推理 ＋ 属性抽取(vLLM) ＋ 检索。

属性抽取三档都走**真实 vLLM 服务**（与 demo 一致），检索都走**真实索引**（单例），因此各段可直接相减，不会口径打架。

### 4.2 一次点击各段耗时（预热后，串行）

优化后的一次点击（用户点"检索相似款"）拆成三段，各段模型**不同**、互不挤占算力：

| 段 | 谁算 | 设备 | 预热后耗时 |
|---|---|---|---|
| ① 属性抽取 | vLLM 8B | GPU0/1 | **~1.36s** |
| ② 视觉 embedding（推理） | 视觉塔 576M | GPU2 | **~0.44s** |
| ③ 检索（按套聚合） | numpy | CPU | **~0.69s** |

串行一次点击 ≈ ①+②+③ ≈ **2.48s**。**注意**：②视觉 0.44s 是**预热后纯推理**；模型加载不在此列——已在启动预热提前消化（见 §4.5）。

### 4.3 向量检索

向量检索**不引入 faiss**，用 numpy 归一化点积即可（44,096 × 1152 一次全量余弦 + 按套聚合），**实测亚秒级**（检索 ~0.69s，含按套聚合、caption 组装等）；库变大可后续换 faiss。索引只放磁盘 / CPU 内存（约 203 MB），不占 GPU；GPU 只放模型。真正的耗时大头是查询图的视觉塔推理 + vLLM 属性抽取，纯检索本身是亚秒级。

### 4.4 角度开关

- **检索侧角度过滤**：`--exclude-side-back`（只留 front/full/flat/additional）、`--angles front,full,...`（自定义允许角度）。
- **展示侧**：`--show best|all`（套缩略图只看最佳角度 / 展开该套所有角度）。

### 4.5 实测效果（三个方案，一条时间线）

同一动作、同一单位（秒）——用户第一次点击到出结果，`scripts/bench_schemes.py` 各 5 次独立进程取均值（逐次见 `logs/bench_schemes.log`）：

```
基准A 原本（整模型，冷启动）
   [ 视觉（加载整模型+推理）46.15s ][ 属性 1.43 ][ 检索 1.01 ] ≈ 48.58s
基准B 视觉塔·冷（未预热）
   [ 视觉（加载视觉塔+推理）10.39s ][ 属性 1.37 ][ 检索 0.68 ] ≈ 12.44s
优化后（视觉塔 + 预热）
   [ 加载视觉塔 10.39s ] ← 启动后台预热消化，点击不等待
   [ 视觉推理 0.44 ][ 属性 1.36 ][ 检索 0.69 ] ≈ 2.48s
```
基准A/B 的「视觉」段是**加载+推理一体**（`bench_schemes.py` 从加载开始计时）；优化后的 0.44s 是**预热后纯推理**。

| 对比 | 总时长 | 加速 |
|---|---|---|
| 基准A → 优化后 | 48.58s → 2.48s | **19.6×** |
| 基准A → 基准B | 48.58s → 12.44s | **3.9×** |
| 基准B → 优化后 | 12.44s → 2.48s | **5.0×** |

**结论**：只加载视觉塔把视觉段（加载+推理）从 46.15s 压到 10.39s（**4.4×**），预热（启动后台 `preload_vision_tower()`）再把**加载**挪出点击路径——用户第一次点击从"等几十秒加载"（≤48.58s）变成"等 2.48s 出结果"（**19.6×**），其中纯推理仅 0.44s。预热省的是"加载那刀"（不是 0.44s）；剩余瓶颈是属性抽取（1.36s，常驻 vLLM）和检索（0.69s），任何方案都要付。这里的加载指**视觉塔抽图时的模型加载**（一次性，即 8.8B→576M 的加载量差），与 `start_web.sh` 的 vLLM 服务启动（~82.7s）不是一回事、不在本优化范围。

> 数值来源：`scripts/bench_schemes.py` 各 5 次独立进程取均值，查询图 `MEN-Denim-id_00000089-28_1_front.jpg`；基准A 对机器负载敏感，本节数值在空闲时测得（load≈2~4，128 核）。

## 5. Gradio 交互（按套入口 / 按角度细化）

1. 上传图 → 一键抽取 18 维属性 → 检索，右侧 Gallery 每格 = **一套穿搭**（缩略图为该套**最佳角度**，caption 标注 `#id · 角度 · 匹配分`）。
2. **点某套缩略图** → 下方预览该套**每个角度**（front/side/additional…，每张标注 `角度 · vis/attr/final`）。
3. **点某个角度图** → 右侧「角度详情」显示该角度自己的信息：`id · 子序号 · 角度 · 视角号 · vis/attr/final` + **该角度的属性**（attrs）。

> 即：**检索、排序、去重的单位是"套"；预览和详情细化到"角度"。**

## 6. 工程纪律

- **属性口径**：检索约束一律用官方 `SHAPE_ATTRS` / `FABRIC_VALS` / `PATTERN_VALS` 映射，与训练数据同源，避免口径漂移。
- **embedding 环境一致性（关键）**：查询 embedding 与索引 embedding 必须来自**同一个 conda 环境 / transformers 版本**。检索相关工作（索引构建、检索、Gradio）**统一用 `vllm` 环境**（transformers 5.8），已验证 cosine=1.0 严格对齐。换版本需重测。
- **GPU 分卡避让**：vLLM 服务与 Gradio 查询模型是不同进程，必须用 `CUDA_VISIBLE_DEVICES` 指定各自所在卡（本机 vLLM 占 GPU0，Gradio 查询模型放 GPU2），避免同卡 OOM。
- **库内查询对照**：内置自检（取库中一张图的 embedding 当查询，应 top-1 命中自身）。
- 索引产物（`index_vectors.npy` / `index_meta.json`）与 `llamafactory/saves` 一致走 git 忽略，不入库。
