# 面试准备

> 这份文档把项目讲清楚：简历怎么写、15 分钟怎么叙述、常见追问怎么答、哪些薄弱点要主动交代。
> 技术细节以[技术报告](技术报告.md)为准，本文只做提炼与话术。

## 1. 简历怎么写

一句话版（投递用）：

> 「基于 Qwen3-VL-8B-Instruct 对 DeepFashion-MultiModal（4.4 万图、18 维官方标注属性）做 LoRA 微调，
> 实现服装图 → 结构化属性 JSON 抽取，并在此基础上落地全库相似款检索；属性级准确率 59.8% → 93.8%（+34.0pp），
> 自建评测体系（属性级 acc / 分层统计 / McNemar / 容错解析），产出 vLLM 部署 demo 与一键复现脚本。」

要点版（面试材料里展开）：

- 任务：服装全身图 → 18 维属性 JSON（12 个形状属性 + 面料 / 图案），一次推理输出完整结构化结果
- 方法：LoRA（r=16、α=32、target=all，可训练 43.6M ≈ 0.5%）+ 冻结视觉塔；训练数据用 schema 感知指令构造
- 结果：属性级准确率 59.8% → 93.8%，macro-F1 0.417 → 0.677，全 JSON 匹配率 47.3%，18 个属性全部 McNemar p<0.001
- 方法归因：8B 上 schema 指令相对朴素指令 +18~31pp，数据量 5k→35k 仅 +1.5pp——提升来自任务工程化而非堆数据；
  换基座到 27B 后同一对照只剩 2.6pp，说明这条结论依赖模型能力（详见下文追问）
- 工程闭环：自建评测体系 → badcase 归因 → 三条干预路线实证（两条负结果）→ vLLM 部署 + 相似款检索

技术关键词（简历技能栏可用）：多模态 SFT / LoRA / 结构化输出与 schema 约束 / 自建评测与显著性检验 /
vLLM 部署 / 向量检索与混合加权 / 数据构造与质量关卡。

## 2. 15 分钟怎么讲

按六段走，每段 2~3 分钟：

1. 动机：电商货架属性靠人工标注，成本高、标准不一、时效差；通用 VLM 能"看图说话"但细粒度属性不可控
   （键名漂移、面料混淆、幻觉输出不可见属性）
2. 方法：LoRA 只训语言塔（ΔW≈BA），冻结视觉塔——视觉塔输出本就是通用特征，要学的是"特征 → 18 维 schema"的映射
3. 数据：官方人工标注、NA/hidden 清洗、按图 80/10/10 防泄漏、类别不均衡用 macro-F1 + 分层兜住
4. 结果：+34.0pp 且 18 属性全部显著；再讲归因（schema 指令是关键、数据效率高），并说明这条归因在 27B 上只剩 2.6pp
5. 失败分析：细粒度混淆与漏检是视觉本质难例；难例续训与约束解码都实证为负，方向只剩解冻视觉塔
6. 工程：schema 感知数据构造、容错解析、评测口径一致、相似款检索、vLLM 部署与一键复现

## 3. 常见追问怎么答

### 3.1 选型与数据

- 为什么用 DeepFashion 不用 ChartQA：业务贴合（电商岗位多）、区分度高（ChartQA 微调同质化严重）、
  细粒度属性基座做不好、提升空间大；ChartQA 只留作 pipeline 验证
- 属性体系哪来的：官方人工标注（Text2Human，SIGGRAPH 2022），定义内嵌在转换脚本的
  `SHAPE_ATTRS` / `FABRIC_VALS` / `PATTERN_VALS`，全表见技术报告 §3.2
- 为什么 attr_json 而不是逐属性 QA：一次推理输出完整结构化结果，贴真实电商场景；attr_qa 同一张图要问 18 次、
  模板高度重复，易过拟合，已弃用
- 类别不均衡怎么处理：主指标用 macro-F1 而非 accuracy；按属性类型 / 类别数分层报告；badcase 驱动补样本
- 怎么防泄漏：按图片粒度 80/10/10（seed 42），三侧图片两两零重叠；test 只在最终评测用一次

### 3.2 训练与资源

- 为什么冻结视觉塔：4 万图量级不大，冻结防过拟合并省显存；解冻需要重训且结果方向不可控，留作对照
- 只训 0.5% 为什么还能涨这么多：分解能力在预训练阶段已具备，LoRA 补的是"任务接口"——
  把通用视觉特征映射到 18 维属性 schema，不是重新学看图
- LoRA rank 怎么定：经验区间 16~64，当前 r=16（8B + 单一抽取任务够用）；过大收益递减且小数据易过拟合
- 单条样本多少 token、会不会截断：视觉 784（782 占位 + 2 标记）+ 文本 369~509 = 完整序列 1,153~1,293，
  远小于 `cutoff_len=2048`，不截断
- 训练成本：基座 8.81B bf16 ≈17.5GB 权重 + LoRA 43.6M；3 卡 DDP 每卡峰值 ≈30.0GB，
  2,793 步约 9.9h（3×4090）

### 3.3 评测与结果

- 为什么强调评测口径一致：评测必须走与训练相同的 llamafactory 管线（同模板、同图像 token 展开、同解码参数），
  否则输出会漂移——实测换成 transformers 原生渲染，30 条里 4 条不一致
- 指标怎么定的：属性级准确率（缺键算错）/ macro-F1（缺键并入 `_missing`）/ 全 JSON 匹配率 / 可解析率，
  定义只在技术报告 §5.1 维护一份
- 47.3% 的全匹配率是不是偏低：全匹配要求 18 个键完全一致，任一键错即判不匹配；按属性级算是 93.8%，
  失败样本里 55% 只错 1 个属性
- 怎么证明不是过拟合：训练全程 28 个 checkpoint 在 val 上验证，曲线在 92.5%~93.8% 平台波动不下降；
  最终 checkpoint 全量确认 93.4%，与峰值持平
- schema 指令到底多重要：要分训练期和推理期。训练期在 8B 上比朴素指令高 18~31pp，但换到 27B 只剩 2.6pp
  （92.0% vs 89.5%）——因为 27B 从 5k 训练答案里就学到了完整键空间（平均缺键 0.14 个/条，8B 是 4.13 个），
  不需要 prompt 枚举；推理期两边都离不开：换成朴素指令后 8B 崩到 0.2%、27B 崩到 0.4%。
  所以训练期的 schema 是补偿小模型的手段，推理期的 schema 是硬性前提

### 3.4 失败分析与工程

- 剩余 6.6% 错误是什么：面料 / 图案的细粒度混淆（视觉边界模糊）、小物件漏检（戒指 / 领饰）、
  多输出 / 漏键（可见性判断）
- 试过哪些改进：难例续训实证为负（全匹配 44.4% < 45.8%）；约束解码 / 后处理能救回的全匹配样本为 0；
  剩下只有解冻视觉塔或换更强视觉基座
- 相似款检索怎么做的：冻结视觉塔抽 embedding + 官方属性命中率加权，按 `(id, 子序号)` 聚合成套；
  只加载视觉塔（576M）并做启动预热，首点耗时从 48.58s 降到 2.48s（19.6×）
- 工程上做过什么取舍：向量检索不引 faiss（numpy 归一化点积够用、索引 203MB 放 CPU）；
  检索与索引必须同环境（已验证 cosine=1.0）；配置里直接写相对路径（框架不解析 `${oc.env:...}` 插值）

## 4. 要主动交代的薄弱点

面试里被问到时如实说，比被戳穿好：

- 划分是图片级、不是套级：按 `(id, 子序号)` 聚合后 test 的 3,825 套里 95% 的同款另一角度图在 train 出现过。
  标注按图独立、同款跨集只提供先验，但对属性抽取影响有限；要严格可改套级划分重评
- 全 JSON 匹配率 47.3%：单键错误即判不匹配，工程上更需要的是属性级准确率与容错解析
- few-shot 不是替代：基座 2-shot 72.3%，仍比微调低 21.1pp，且每次推理要带示例
- 没有做解冻视觉塔、多任务组合、未见品类泛化：都列进了"暂不纳入"并写明理由（成本高、方向不可控）
- 单一数据集、单一模型规模：结论的可迁移性靠"任务工程化 + 轻量微调 + 严谨评测"这套方法，
  而不是某个特定模型

## 5. 可以反问面试官

- 团队现在的属性体系是自建还是沿用平台的？标注成本大概什么量级？
- 结构化抽取这块，线上更看重属性级准确率还是整段 JSON 可用率？
- 视觉侧有没有预算解冻视觉塔 / 换更大基座，还是更倾向数据侧投入？
