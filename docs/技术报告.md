# DeepFashion 服装属性提取与相似款检索：技术方案与实验报告

> 项目定位：基于 Qwen3-VL-8B-Instruct，用 LLaMA-Factory 对 DeepFashion-MultiModal 时装数据集（SIGGRAPH 2022，4.4 万图、18 维官方标注属性）做 LoRA 微调，实现「服装全身图 → 结构化属性 JSON」抽取，并在抽取结果之上落地相似款检索（属性 + 视觉混合加权，全库 top-k 相似款），升级为「电商标注 + 相似款检索」完整闭环，对标电商货架属性 / 商品知识图谱 / 相似款推荐场景。
>
> 核心结果：test 集属性级准确率 59.8% → **93.8%（+34.0pp）**，macro-F1 0.417 → 0.677，McNemar 检验 p<0.001，JSON 可解析率 100%；消融证明 schema 感知指令在 8B 上是关键方法（+31.5pp），但收益随基座变强而收窄（27B 上仅 2.6pp，见[换基座实验](换基座实验.md)），训练稳定无过拟合；相似款检索在部署 demo 上落地。

## 1. 背景与动机

### 1.1 业务痛点

电商平台的商品属性数据是基础设施：货架属性决定商品如何被展示，搜索标签决定商品如何被召回，商品知识图谱决定关联推荐的质量。目前这些属性大量依赖人工标注，存在三个问题：

- 成本高：全量人工标注覆盖海量 SKU 不现实，长尾商品覆盖差；
- 标准不一：不同标注员对同一件衣服的袖长、面料判断不一致；
- 时效差：上新速度快，人工标注跟不上。

### 1.2 通用 VLM 的局限

通用多模态大模型（如 Qwen3-VL）具备基础的图像理解能力，可以直接"看图说话"，但对细粒度结构化属性抽取存在系统性缺陷：

- 格式不稳定：输出自由文本，不保证是合法 JSON，键名随意漂移；
- 属性混淆：细粒度属性（medium-sleeve vs long-sleeve、cotton vs knitted、pure color vs color block）边界模糊，张冠李戴；
- 幻觉：输出图上不可见的属性（NA/hidden 误报）。

### 1.3 方案定位

用领域数据对 VLM 做轻量 LoRA 微调，把"通用理解"变成"业务可用的结构化抽取能力"，并把抽取结果用于相似款检索，形成「标注 + 检索」的完整电商闭环。同时给出完整的评测证据链——不是"训完就完"，而是可量化、可归因、可复现的工程闭环。

## 2. 技术方案总览

```
用户上传服装全身图
        │
        ▼
┌─ 结构化属性抽取（主线）─────────────────────────────┐
│  数据：DeepFashion-MultiModal 4.4 万图 / 18 维属性     │
│  方法：Qwen3-VL-8B + LoRA 微调（冻结视觉塔，schema 指令）│
│  评测：自建指标 + McNemar + 消融（93.8% acc）         │
└───────────────┬──────────────────────────────────┘
                │  属性 JSON + 视觉 embedding
                ▼
┌─ 相似款检索（应用闭环）─────────────────────────────┐
│  属性约束过滤 + 向量余弦混合加权 → 全库 top-k 相似款     │
│  Gradio Gallery 展示（图上标匹配分）                  │
└───────────────┬──────────────────────────────────┘
                ▼
        vLLM 部署 demo（CLI / Web）
```

技术主线为结构化属性抽取（数据 → 微调 → 评测，证据链完整）；相似款检索是抽取结果之上的应用出口，把项目串成「电商标注 + 相似款检索」的完整电商场景。

## 3. 数据与任务

本节给出数据集、18 维属性体系与任务定义；数据的获取与处理（目录组织、下载解压、转换脚本、框架接入、样本格式）见[数据说明](数据说明.md)，端到端命令序列见[复现说明](复现说明.md)。

### 3.1 为什么用 DeepFashion-MultiModal

| 维度 | ChartQA（备选） | DeepFashion-MultiModal（选定） |
|---|---|---|
| 区分度 | 模板化微调，方案同质化 | 用的人极少，组合几乎空白 |
| 业务匹配 | BI/报表问答，岗位少 | 电商/内容平台岗位多，价值直观 |
| 微调收益 | base 模型已不差，提升空间有限 | 细粒度属性 base 做不好，容易出大提升 |
| 评测基准 | 官方 ground truth | 无官方指标 → 自建体系（展示方法论） |
| 数据形态 | 合成图表 | 真实人像/衣物图，demo 冲击力强 |
| 成本 | 子集小、快 | 4.4 万图，8B 单卡可控（`max_samples` 限流） |

选定数据集的基本信息：

| 项 | 内容 |
|---|---|
| 数据集 | DeepFashion-MultiModal（Text2Human，SIGGRAPH 2022），官方人工标注，无版权风险、可公开复现 |
| 规模 | 44,096 张 750×1101 全身人像图；`captions.json` 42,544 条描述 |
| 标注 | 12 个形状属性 + 上 / 下 / 外装各自的面料与图案 |
| 依赖文件 | `images.zip` / `labels.zip` / `captions.json`（segm / densepose / keypoints 与任务无关，可不下） |

主线数据 = DeepFashion-MultiModal（attr_json 任务）；ChartQA 仅作为 pipeline 验证（两套数据脚本同构，切换成本低）。两点注意：数据发布于 2022 年 → 强调"任务不变、方法新"（以 Qwen3-VL 刷新旧 benchmark 基线）；标签含 NA/hidden 噪声 → 转换时剔除不可见属性，评测与训练口径一致。

### 3.2 属性体系

| 属性键 | 中文名 | 可选取值 |
|---|---|---|
| `sleeve_length` | 袖长 | sleeveless（无袖）/ short-sleeve（短袖）/ medium-sleeve（中袖）/ long-sleeve（长袖）/ not long-sleeve（非长袖） |
| `lower_clothing_length` | 下装长度 | three-point（三分，短款）/ medium short（中短）/ three-quarter（七分）/ long（长） |
| `socks` | 袜子 | no（无）/ socks（袜子）/ leggings（打底裤） |
| `hat` | 帽子 | no（无）/ yes（有） |
| `glasses` | 眼镜 | no（无）/ eyeglasses（框架眼镜）/ sunglasses（太阳镜）/ glasses in hand or on clothes（拿在手中或挂在衣服上） |
| `neckwear` | 颈饰（围巾 / 项链等） | no（无）/ yes（有） |
| `wrist_wearing` | 手腕佩戴物 | no（无）/ yes（有） |
| `ring` | 戒指 | no（无）/ yes（有） |
| `waist_accessories` | 腰部配饰 | no（无）/ belt（腰带）/ clothing at waist（系在腰间的衣物）/ hidden（被遮挡） |
| `neckline` | 领型 | V-shape（V 领）/ square（方领）/ round（圆领）/ standing（立领）/ lapel（翻领）/ suspenders（背带 / 吊带） |
| `outer_clothing_is_cardigan` | 外衣是否为开衫 | yes（是）/ no（否） |
| `upper_clothing_covering_navel` | 上衣是否遮住肚脐 | no（否，露脐）/ yes（是） |
| `{upper,lower,outer}_fabric` | 面料（上 / 下 / 外装） | denim（牛仔）/ cotton（棉）/ leather（皮革）/ furry（毛绒）/ knitted（针织）/ chiffon（雪纺）/ other（其他） |
| `{upper,lower,outer}_pattern` | 图案（上 / 下 / 外装） | floral（碎花）/ graphic（图形）/ striped（条纹）/ pure color（纯色）/ lattice（格纹）/ other（其他）/ color block（色块） |

- 构成：18 维 = 12 个形状属性 + 3 个部位（上装 / 下装 / 外装）各自的面料与图案
- 定义来源：官方 README（[yumingj/DeepFashion-MultiModal](https://github.com/yumingj/DeepFashion-MultiModal)），同一份定义内嵌在 `scripts/data_convert_deepfashion_multi.py` 的 `SHAPE_ATTRS` / `FABRIC_VALS` / `PATTERN_VALS`
- 取值写法：上表按「英文值（中文含义）」给出，英文值是数据字段里的实际取值
- 组合键：面料与图案两行用 `{upper,lower,outer}` 指代上衣 / 下装 / 外衣，三个部位的取值集合各自一致
- 缺失值：所有属性都允许 NA（不可见），`waist_accessories` 另允许 hidden（被遮挡）；两者在转换时按无效值剔除
- 输出范围：转换时只保留可见属性，`outer_*` 仅在图中存在外衣时出现，每图实际输出 10~16 个键
- 标注文件：12 个形状属性来自 `labels/shape/shape_anno_all.txt`；面料与图案分别来自 `labels/texture/fabric_ann.txt` 与 `labels/texture/pattern_ann.txt`（各三列，依次对应上装 / 下装 / 外装）

### 3.3 任务形态与数据格式

| 任务（注册名前缀） | 输入 → 输出 | 数据量（train / val / test） | 结论 |
|---|---|---|---|
| `deepfashion_attr_json_*` | 图 + schema 枚举指令 → 完整属性 JSON | 35,276 / 4,410 / 4,410 | 主线 |
| `deepfashion_attr_json_simple_*` | 图 + 朴素一句话指令 → 完整属性 JSON | 35,276 / 4,410 / 4,410 | 对照 |
| `deepfashion_caption_*` | 图 → 自然语言描述 | 34,006 / 4,258 / 4,273 | 辅助，多任务组合暂未纳入（见 §6.1） |
| `deepfashion_attr_qa_*` | 逐属性单问 → 单值 | 451,744 / 56,860 / 56,943 | 弃用：同一张图要问 18 次、模板重复易过拟合 |

选 `attr_json` 做主任务的理由是"一次推理给出完整结构化输出"——贴合真实电商抽取场景，评测又能按属性键解构。数据划分策略与防泄漏处理见 §3.5。

### 3.4 主线任务 `attr_json`

为什么用 attr_json 做主任务：一次推理输出完整结构化属性，贴合真实电商抽取场景；输出为 JSON，与「图像 → 结构化输出」主线一致；评测可按属性键解构，严谨且细粒度。

schema 感知指令由 `build_schema_prompt()` 从属性表自动生成，训练 / 评测共用同一份原文，分三段：

1. 任务句：`Extract the clothing attributes visible in this image and output a JSON object.`
2. `Allowed keys and values`：枚举全部 18 个属性键及每键合法取值
3. `Rules`：三条输出规则（只输出可见属性 / 只用合法取值 / 只输出 JSON）

```
Extract the clothing attributes visible in this image and output a JSON object.

Allowed keys and values:
- sleeve_length: sleeveless, short-sleeve, medium-sleeve, long-sleeve, not long-sleeve
- lower_clothing_length: three-point, medium short, three-quarter, long
- socks: no, socks, leggings
- hat: no, yes
- glasses: no, eyeglasses, sunglasses, glasses in hand or on clothes
- neckwear: no, yes
- wrist_wearing: no, yes
- ring: no, yes
- waist_accessories: no, belt, clothing at waist
- neckline: V-shape, square, round, standing, lapel, suspenders
- outer_clothing_is_cardigan: yes, no
- upper_clothing_covering_navel: no, yes
- upper_fabric: denim, cotton, leather, furry, knitted, chiffon, other
- upper_pattern: floral, graphic, striped, pure color, lattice, other, color block
- lower_fabric: denim, cotton, leather, furry, knitted, chiffon, other
- lower_pattern: floral, graphic, striped, pure color, lattice, other, color block
- outer_fabric: denim, cotton, leather, furry, knitted, chiffon, other
- outer_pattern: floral, graphic, striped, pure color, lattice, other, color block

Rules:
- Include only keys whose attribute is clearly visible in the image.
- Use only the allowed values listed above.
- Output the JSON object only, without any extra text or explanation.
```

- 稳定性：键与取值顺序由属性表决定，训练 / 评测 / 推理三端一致
- 对照版：`simple` 只保留任务句（`Extract the clothing attributes visible in this image and output them as JSON.`），不枚举键与取值；两者效果差异见 [report_ablation.md](../experiments/qwen3vl8b/ablation/reports/report_ablation.md)
- 样本结构：sharegpt 格式见[数据说明 §5 样本格式](数据说明.md#5-样本格式)

### 3.5 数据准备与质量保障

- 准备流程：下载 → 解压 → 转换 → 质检；前两步的命令见[数据说明 §2](数据说明.md#2-获取与解压)，转换与清洗细节（可见属性筛选、空 caption 清理、图片按内容哈希去重、`dataset_info.json` 注册）见同文[§3](数据说明.md#3-转换为训练数据)
- 划分：按图片粒度 80/10/10（seed=42），三侧图片两两零重叠——同一张图的所有样本必在同一侧；test 只在最终评测用一次
- 已知风险（套级跨集）：按 `(id, 子序号)` 聚合后，test 的 3,825 个"套"里有 95% 在同一款衣服的另一角度图出现在 train（val 同样 95%，test∩val 另 27%）；原因是同款不同角度被 `random(seed=42)` 打散到三侧
  - 不影响结论：防泄漏的硬约束是"同一张图绝不跨集"，图片级划分已经满足
  - 标注按图独立：同款不同角度的可见属性本就不同（正面有领型、侧面可能看不到），test 那张图及其标注从未进过 train
  - 影响有限：同款跨集只提供"这件衣服"的先验，而 test 图是未见角度、判定仍要从图本身提取；改套级可彻底消除先验，但 test 套数会骤减

数据质量四关卡（`python scripts/check_data.py`）：

| 关卡 | 检查内容 | 当前状态 |
|---|---|---|
| 1. schema 健全 | sharegpt 结构、`<image>` 占位符、图片文件存在 | ✅ |
| 2. 答案合法 | assistant JSON 可解析、键 / 值在官方表内、无空答案 | ✅ |
| 3. 防泄漏 | train/val/test 三侧图片两两零重叠 | ✅ |
| 4. 分布统计 | 每属性类别分布（不均衡预览）→ `experiments/qwen3vl8b/main/reports/data_stats.json` | ✅ |

已知不均衡点（影响评测设计）：多分类属性（sleeve_length / neckline / fabric / pattern）长尾明显（如 `suspenders`、`furry` 样本少）；评测用 macro-F1 + 分层，避免被 majority 类掩盖。

## 4. 模型与训练

### 4.1 基座模型

基座：Qwen3-VL-8B-Instruct（`Qwen3VLForConditionalGeneration`，全模型 bf16）

据训练实际使用的 `models/Qwen3-VL-8B-Instruct/config.json`（语言+视觉结构；模型参数量以训练日志实测 `all params = 8.81B` 为准）：

| 部分 | 参数 | 数值 |
|---|---|---|
| 语言主干 | hidden_size | 4,096 |
| | 层数 / 注意力头 / KV 头 | 36 / 32 / 8（head_dim=128） |
| | 中间层 FFN | 12,288 |
| | 词表 / max_position_embeddings | 151,936 / 262,144 |
| 视觉塔 | hidden_size / 层数 | 1,152 / 27（`deepstack` 索引 8/16/24 分层缩并） |
| | 注意力头 / 中间层 | 16 / 4,304 |
| | patch / 输出 | patch_size=16、temporal_patch 2、`out_hidden=4,096`（对齐语言） |
| 总量 | ≈ 8.81B | 语言 + 视觉 + 多模态投影器，全 bf16（训练日志实测 `all params = 8,810,770,672`） |

### 4.2 LoRA 微调与冻结视觉塔

LoRA 微调（实际训练记录 `experiments/qwen3vl8b/main/weights/lora/qwen3vl8b_dfattr_lora/training_args.yaml`）

| 项 | 配置 |
|---|---|
| 基座 | Qwen3-VL-8B-Instruct（≈ 8.81B 参数，全部冻结，仅训练 LoRA） |
| 微调方式 | LoRA（`r=16`、`alpha=32`、`dropout=0.05`、`target=all` → q/k/v/o/gate/down/up 共 7 个投影），可训练 ≈ 43.6M 参数（约 0.5%） |
| 优化 | AdamW，`lr=1e-4`，cosine 调度，`warmup=150` 步，`max_grad_norm=1.0` |
| 训练 | 3 epoch，等效 batch 36（`per_device=4` × 3 卡 DDP × `accum=3`），3×48GB RTX 4090，共 2,793 步 |
| 冻结 | 冻结视觉塔 + 多模态投影器（小数据防过拟合 + 省显存），仅 LoRA 可训练 |
| 模板 | `qwen3_vl_nothink`（训练-推理一致、关闭 thinking） |
| 图像 | `image_max_pixels=825,750`（原图 750×1101 像素，不压缩档：原图像素数、不主动缩小，训练-推理口径统一）、`image_min_pixels=1024` |
| 训练数据 | `deepfashion_attr_json_train`（35,276 条，`val_size=0.05` 切出 5% 后实际训练 ≈ 33,512 条/epoch） |
| 训练监控 | `logging_steps=10`、每 100 步存 checkpoint + 做一次 val eval（28 个点），`train_loss 0.564 → 0.017`，最终选 checkpoint-2793 |

> 以上数值取自实际训练产物（`training_args.yaml` / `adapter_config.json` / `trainer_state.json` / `all_results.json`），非估算：训练用时 ≈ 35,693s（约 9.9h，3×4090），`train_runtime`，`eval_loss=0.021`（语言建模口径，仅作过拟合监控）。

为什么冻结视觉塔 + 低秩 LoRA 仍能到 93.8%（面试高频追问）：
- 核心机制：视觉塔（Qwen3-VL 预训练编码器）输出的本就是通用视觉特征，冻结它 = 特征提取器不变，LoRA 只微调语言塔、把视觉特征映射到本项目 18 维属性 schema——学"对齐"而非重新学看图；
- 参数少也够：可训练仅 43.6M（0.5%）是因为分解能力预训练已有，LoRA 只补"任务接口"；`r=16` 是 8B + 单一抽取任务的稳妥起点（经验区间 16~64），过大收益递减、易过拟合小数据；
- 不解锁视觉塔：全训 27 层 × 1,152 参数更贵、小数据易过拟合，留作对照（见 §6.1）。

### 4.3 训练输入与执行

单条样本规模（`cutoff_len=2048` 不截断，实测确认）：

| 项 | 实测 |
|---|---|
| 视觉 token（进 LLM） | 784 = 782 占位 + 2 标记（推算过程见[训练说明](训练说明.md)） |
| 文本 token（prompt+答案） | ≈369~509（平均 ≈459；随 JSON 答案长度浮动，100 条真实样本实测） |
| 完整序列 = `input_ids` 长度 | ≈1,153~1,293（平均 ≈1,243）—— 即文本 + 784 个视觉 token，实测 100 条样本 |
| `cutoff_len=2048` 判定 | 完整序列 1,153~1,293 < 2048 → 不截断，答案完整保留 |

训练命令（单机多卡自动走 DDP，默认用全部可见 GPU；本机 3 卡，等效 batch = 4×3×3 = 36）：

```bash
llamafactory-cli train experiments/qwen3vl8b/main/config/qwen3vl8b_dfattr_train_cli.yaml
# 单卡：CUDA_VISIBLE_DEVICES=0 限制，并把配置文件里 gradient_accumulation_steps 改为 9
```

训练中按现象处理：

| 现象 | 动作 |
|---|---|
| 欠拟合（val 不涨） | 升 lr / 加 epoch / 解冻视觉塔 |
| 过拟合（val 先升后降） | 降 lr / 加 dropout / 减数据 / 冻结视觉塔 |
| JSON 输出乱 | 确认 `qwen3_vl_nothink` 生效；训练前打印渲染样本 |
| 显存溢出 | 降 batch；确认 gradient_checkpointing 开启 |

## 5. 评测体系

### 5.1 指标定义

| 指标 | 口径 | 说明 |
|---|---|---|
| 属性级准确率 | 每个属性键 pred==true 比例 | 主指标；预测缺键算错（暴露漏检） |
| 属性级 macro-F1 | 多分类 F1 平均，缺键并入 `_missing` 类 | 对抗类别不均衡 |
| 全 JSON 匹配率 | 解析结果 == 真值 dict 精确一致 | 严格指标 |
| JSON 可解析率 | 输出能解析为 dict 的比例 | ≥98% 达标；格式错误单独统计 |

容错解析三级策略（`scripts/eval_attr.py` 实现）：① 提取首个 `{...}` 区间 → `json.loads`；② 失败则从右截断至最后一个完整键值对；③ 仍失败记「格式错误」。

### 5.2 对比组设计与统计检验

- 对比组：Base 0-shot（基座 + 同一 schema 指令） vs LoRA——评测代码、数据集、prompt 三者完全一致，唯一变量是"是否微调"；
- McNemar 检验（配对二分类、连续校正）：逐属性 + 总体，p<0.05 才下结论；
- 分层统计：按属性组（形状/面料图案）、按类别数（二分类/多分类）分别报告，避免被 majority 类掩盖；按品类泛化（加分项）：按图名前缀（MEN/WOMEN + 品类）统计准确率，⚠️ 真正"未见品类泛化"需按品类整体划分数据并重训（当前按图随机划分下，test 品类在 train 均出现过）。

### 5.3 评测口径一致性

评测结果的可信度取决于评测与训练的输入是否完全同口径。本项目评测生成统一走 llamafactory 管线（与训练同模板 `qwen3_vl_nothink`、同多模态图像 token 展开、同数据格式、同解码参数 greedy），打分由自建 `eval_attr.py` 承担。这一做法源于一次实证发现：若评测改用 transformers 原生渲染（1 个图像占位符 vs 训练时的显式 6~7 个图像 token 展开），30 条实测会有 4 条输出漂移（属性级 99% 一致、文本 87% 一致）——评测必须与训练同口径。

### 5.4 评测执行

预测生成统一走 llamafactory 管线（与训练 100% 同口径），`scripts/eval_attr.py` 只承担 `stats` 打分（原因见 §5.3）。一次评测分两步：

1. `convert_preds.py`：把 llamafactory 的 `generated_predictions.jsonl` 转成预测文件（base / lora 各一份）；
2. `eval_attr.py stats`：读两份预测，产出属性级指标、分层统计与 McNemar。

开发阶段在 val 上反复跑（模型选择、调参），最终报告只在 test 上跑一次——把 val 两份配置复制为 test 版、`eval_dataset` 改成 `deepfashion_attr_json_test`。完整命令见[复现说明](复现说明.md)的评测一节。

## 6. 实验结果

### 6.1 实验设计与对照矩阵

> 组织方式按论证链分四环：效果（微调是否有效）→ 归因（提升来自哪里）→ 边界（效果依赖与鲁棒性）→ 过程（训练稳定性）。主结果与基座规模在 test 上报告（全程只碰一次），其余对照在 val 集评测；口径统一为 llamafactory 管线生成预测 + `eval_attr.py stats` 打分。

| 论证环节 | 实验 | 变量 | 变更方式 |
|---|---|---|---|
| 效果 | 主结果 | 是否微调 | Base vs LoRA，test 4,410 条；McNemar 显著性 + 属性分层 |
| 效果 | 品类分层 | 图片品类 | 按图名前缀（MEN/WOMEN + 品类）统计准确率，检验泛化是否依赖品类 |
| 归因 | 指令范式 × 数据量 | 训练指令 / 数据规模 | schema vs simple × 5k/20k/35.3k，同一组 6 配置双轴解读 |
| 归因 | LoRA 秩 | r ∈ {8,16,32} | `lora_rank: 8`（可选） |
| 边界 | 指令鲁棒性 | 推理期指令 | 同一模型换 simple prompt 评测（与归因"指令范式"互补） |
| 边界 | few-shot 对照 | 示例数量 | 基座 + 2 个 in-context 示例，回答"为什么微调不 few-shot" |
| 边界 | 图像分辨率 | 评测输入分辨率 | `image_max_pixels` 589,824 vs 825,750（推理端） |
| 边界 | 基座规模 | 基座 | 换 Qwen3.8-27B 复跑全套实验（test 主结果 + 5k 两格消融 + checkpoint 快筛），检验结论是否随基座迁移 |
| 过程 | Checkpoint 选择 | 训练步数 | 28 个 checkpoint 抽样快筛（500 条）+ 关键点全量确认，选最优定稿 test |

暂不纳入：视觉塔冻结 vs 解冻（解冻训练慢、结果方向不可控）；任务组合 attr_json vs +caption 多任务（成本最高、收益叙事一般）；未见品类泛化（需按品类整体划分数据并重训，成本高）。

### 6.2 微调效果

#### 6.2.1 主结果

| 指标 | Base 0-shot | LoRA | 提升 |
|---|---|---|---|
| JSON 可解析率 | 100.0% | 100.0% | —（达标 ≥98%） |
| 全 JSON 匹配率 | 0.0% | 47.3% | +47.3pp |
| 属性级准确率 | 59.8% | **93.8%** | **+34.0pp** |
| macro-F1 | 0.417 | 0.677 | +0.260 |
| McNemar（总体） | — | p < 0.001（b=20106, c=833） | 极显著 |

逐属性：18 个属性全部显著提升（McNemar 逐属性 p 均 < 0.001），提升最大的是 `upper_clothing_covering_navel`（+76.0pp）、`lower_clothing_length`（+69.2pp）、`glasses`（+46.8pp）；提升最小的是 `sleeve_length`（+3.5pp，基座已达 91.8%，接近饱和）。

#### 6.2.2 属性分层

| 分层 | Base 0-shot | LoRA | Δ |
|---|---|---|---|
| shape 属性（12 个） | 56.8% | 96.3% | +39.6pp |
| texture 属性（6 个） | 65.8% | 88.6% | +22.8pp |
| 二分类（6 个） | 54.3% | 96.7% | +42.4pp |
| 多分类（12 个，细粒度难点） | 62.5% | 92.3% | +29.8pp |

#### 6.2.3 品类分层

按图片品类统计（与属性分层是不同维度）：

- 覆盖面：全部 23 个品类准确率区间 90.1%~100%，表现均衡，无灾难性品类
- 大品类：样本量 top3（`Tees_Tanks` / `Blouses_Shirts` / `Dresses`）93.8%~96.4%
- 性别维度：MEN 96.6% vs WOMEN 94.6%（女装品类属性更多样）

三条合起来说明：模型泛化不依赖特定品类。

解读：三个证据共同支撑"微调有效"——① 总体提升 +34.0pp 且 McNemar 极显著；② 对各类属性类型（判断类 +40pp 级、细粒度多分类 +30pp 级）普适；③ 跨品类表现均衡（90%+），效果不是某一类衣服的偶然。

### 6.3 提升归因

主结果回答"是否有效"，本节回答"为什么有效"——把 +34pp 的提升拆解为可解释的来源。消融在 val 集（4,410 条）评测，按指令范式（schema/simple）× 数据量（5k/20k/35k）二维展开，每次对比保持唯一变量。同一组 6 个训练配置构成如下二维矩阵（val 集属性级准确率），横向（行内）与纵向（列内）各持一个唯一变量：

| 训练指令 | 5k | 20k | 35k（全量） | Δ(5k→35k) |
|---|---|---|---|---|
| schema | 91.9% | 92.9% | **93.4%** | +1.5pp |
| simple | 60.4% | 74.0% | 75.3% | +14.9pp |
| Δ(schema−simple) | +31.5pp | +19.0pp | +18.1pp | — |

*表注：纵向（列内）比较 = 指令范式消融（唯一变量=训练指令）；横向（行内）比较 = 数据量消融（唯一变量=训练数据量）。*

另外两个指标按同一二维排列（35k 为全量训练数据，加粗格为最终主模型）：

macro-F1：

| 训练指令 | 5k | 20k | 35k（全量） |
|---|---|---|---|
| schema | 0.631 | 0.664 | **0.670** |
| simple | 0.425 | 0.511 | 0.518 |

全 JSON 匹配率：

| 训练指令 | 5k | 20k | 35k（全量） |
|---|---|---|---|
| schema | 37.8% | 43.6% | **45.8%** |
| simple | 0.0% | 0.0% | 0.0% |

**沿指令轴**（schema vs simple）——在 8B 这一档模型上，指令范式是决定性方法：相同数据与训练配置下，枚举合法键/取值的指令始终显著优于朴素指令。优势随数据量增大而收窄（+31.5pp→+18.1pp），但朴素指令用全量数据（35k）也只有 75.3%，仍不及 schema 指令用 5k 数据（91.9%）的水平；macro-F1 同样全面落后（补充指标表中全量 0.670 vs 0.518），且 simple 版在三个数据量下全 JSON 匹配率恒为 0.0%（输出从不按 18 维 schema 对齐）。指令设计决定了结构化输出的成败——这是任务工程化的方法论收益，直接支撑 §3.4 的设计动机。schema 指令的重要性不止于训练期：推理期若把评测指令替换为 simple，效果同样崩塌（见 §6.4.1）。

**沿数据轴**（5k→20k→35k）——数据效率极高、堆数据事倍功半：schema 曲线平缓——数据量从 5k 增至 35.3k 属性级准确率仅 +1.5pp，且收益集中在前 20k（5k→20k +1.0pp、全 JSON 匹配率 +5.8pp；20k→35k 边际递减 +0.5pp/+2.2pp），更多数据主要帮助整段 JSON 的完整性（少漏键、少缺属性），schema 指令下模型数据效率极高（5k 即达 92% 水平）；simple 曲线陡峭——数据收益 +14.9pp 几乎全被"追赶指令差距"消耗（20k 即 +13.6pp 后趋平），说明没有好的指令设计，堆数据事倍功半。

归因小结：在 8B 上，提升主要来自任务工程化（schema 指令设计）而非数据堆量，双向验证：schema 用 1/7 数据（5k）拿到 91.9%，simple 用全量数据（35k）只有 75.3%——这与"电商标注贵"的业务痛点直接呼应：好的任务设计可以用很少的数据拿到大部分收益。这条归因以 8B 为条件，边界见 §6.4.4。

### 6.4 适用边界

主结果与归因证明"微调有效、来自方法"，本节划定这套效果的适用边界。前三个对照均在 val 集评测、模型为同一最终模型（或基座）；第四个换掉基座，用来检验上面的结论对模型规模的依赖。

#### 6.4.1 指令鲁棒性

本节与 §6.3 指令轴互补：§6.3 更换的是训练指令（重训两组模型，测得方法收益 +18~31pp），本节更换的是推理指令（模型不变，测得运行依赖）——同一变量（schema/simple）在训练期与运行期的两个作用阶段。

| 指令 | 属性级准确率 | JSON 可解析率 | 全 JSON 匹配率 |
|---|---|---|---|
| schema prompt（与训练一致） | 93.4% | 100.0% | 45.8% |
| simple prompt | 0.2% | 99.7% | 0.0% |

在 simple 朴素指令下，LoRA 模型输出退化为自由格式 JSON（键名如 `top.type`、`clothing[].color`，不再是 18 维属性键名），按任务 schema 对齐后属性级准确率仅 0.2%（JSON 可解析率 99.7% 说明是合法 JSON 但结构不对齐）。schema 指令是运行期必需：业务部署必须携带 schema prompt。这与 §6.3 指令轴解读互相印证——训练期"有它 +31.5~18.1pp"（方法收益），推理期"没它 -93.2pp"（运行依赖）。

#### 6.4.2 few-shot 对照

| 模型×指令 | 属性级准确率 | 全 JSON 匹配率 |
|---|---|---|
| Base 0-shot（schema） | 59.9% | 0.0% |
| Base 2-shot（schema + 2 示例） | 72.3% | 0.1% |
| LoRA（schema） | 93.4% | 45.8% |

基座 2-shot 较 0-shot 提升 +12.4pp（in-context 示例确有帮助），但仍比微调低 21.1pp，且每次推理需额外携带示例输入——用数据回答"为什么微调而不 few-shot"：few-shot 无法达到结构化抽取的业务可用水平。

#### 6.4.3 图像分辨率

| image_max_pixels | 属性级准确率 | 全 JSON 匹配率 |
|---|---|---|
| 825,750（不压缩，与训练一致） | 93.4% | 45.8% |
| 589,824（压缩） | 93.0% | 44.0% |
| Δ | -0.4pp | -1.8pp |

评测输入压缩到 768×768 仅造成 -0.4pp 损失——模型对输入分辨率鲁棒；评测口径维持与训练一致（不压缩）。

#### 6.4.4 基座规模

把主实验基座换成 Qwen3.8-27B（27.36B）复跑全套实验，检验前面的结论是否随基座迁移。先看主结果（test，全量 4,410 条）：

| 指标（test） | 8B | 27B | Δ |
|---|---|---|---|
| 属性级准确率 · Base 0-shot | 59.8% | 82.9% | +23.1pt |
| 属性级准确率 · LoRA | 93.8% | 93.7% | −0.1pt |
| 全 JSON 匹配率 · Base 0-shot | 0.0% | 1.8% | +1.8pt |
| 全 JSON 匹配率 · LoRA | 47.3% | 49.6% | +2.3pt |
| macro-F1 · Base 0-shot | 0.417 | 0.521 | +0.104 |
| macro-F1 · LoRA | 0.677 | 0.682 | +0.005 |

再看「训练期 schema 指令值多少」——同样 5k 数据、唯一变量是训练指令（val 全量 4,410 条）：

| 训练配置（5k 数据） | 8B | 27B |
|---|---|---|
| schema 指令 | 91.9% | 92.0% |
| simple 指令 | 60.4% | 89.5% |
| 换成 simple 的代价 | −31.5pt | −2.6pt |

两张表给出三层结论：

- 基座层面：27B 三个指标全面领先——准确率 +23.1pt、全 JSON 匹配率从 0% 到 1.8%、macro-F1 +0.104
- 微调后：绝对水平打平（准确率 −0.1pt），但严格口径仍是 27B 更好——全匹配 +2.3pt、macro-F1 +0.005
- 方法结论：训练期 schema 的收益从 31.5pt 收窄到 2.6pt，同一个 simple 格上 27B 还比 8B 高 29.1pt。原因是输出空间的学习方式——27B 用 5k 就能学到完整的键空间（平均缺键 0.14 个/条，8B 为 4.13 个），8B 加到 7 倍数据仍差一个数量级（1.85 vs 0.19）

由此，「schema 指令是决定性方法」只在模型无法自行补全输出空间时成立；模型够强时训练期指令退化为加速项，而推理期的依赖不变——两个基座都必须携带 schema prompt（27B 换成 simple 后同样崩到 0.4%）。完整结果、两格消融与 checkpoint 快筛见[换基座实验](换基座实验.md)。

边界小结：

| 边界 | 结论 |
|---|---|
| schema 指令 | 训练与部署都必须在场，两个基座都成立 |
| few-shot | 不是可行替代，仍低微调 21.1pt |
| 输入分辨率 | 不敏感，压缩只掉 0.4pt |
| 基座规模 | 训练期 schema 的必要性随基座变强而下降，推理期不变 |

### 6.5 训练过程

对训练全程 28 个 checkpoint 抽样 15 个点，在 val 上评测（500 条快筛 + 关键点全量确认）：

```
100步  90.4%   300步 91.3%   500步 92.1%   700步 92.5%
900步  93.8%  ← 峰值（约 1 epoch）
1100步 92.6%   1300步 92.8%   ...   2100步 93.8%（第二峰值）
2500步 93.4%   2793步 93.4%（最终）
```

全量确认（4,410 条 val）：ckpt-900 93.3% / ckpt-2100 93.4% / **ckpt-2793（最终）93.4%**（macro-F1 0.670 最优）。

结论：① LoRA 收敛极快——训练 100 步（约 3% 数据）即达 90.4%；② 全程无过拟合——曲线在 92.5%~93.8% 平台波动、不下降，3 epoch 是稳妥选择；③ 最终 checkpoint 在 macro-F1 与全 JSON 匹配率上略优，用作 test 定稿模型——模型选择有据可依，不是拍脑袋。

## 7. 错误分析

对 val 集 4,410 条预测中 LoRA 模型的错误进行统计（4,410 条中 2,391 条未达全 JSON 匹配），错误模式如下：

### 7.1 错误分布

错误最多的属性集中在 texture 组：`lower_fabric`（440 次）、`upper_fabric`（394 次）、`upper_pattern`（333 次）、`lower_pattern`（276 次）——材质与图案是视觉上最难区分的细粒度维度。

### 7.2 典型混淆对

| 属性 | 混淆 | 次数 | 归因 |
|---|---|---|---|
| 面料 | `chiffon → cotton` / `cotton → chiffon` / `cotton → denim` | 179 / 111 / 104 | 轻薄面料 vs 棉 vs 牛仔的纹理相似，视觉边界模糊 |
| 戒指 | `ring: yes → no` | 113 | 小物件漏检（遮挡/尺寸小） |
| 图案 | `graphic → pure color` | 92 | 图案细节丢失（远景/小图） |
| 领饰 | `neckwear: yes → no` | 78 | 小物件漏检 |
| 袖长 | `medium-sleeve → long-sleeve` | 76 | 细粒度边界（中袖 vs 长袖） |
| 腰饰 | `waist_accessories: no → 缺键` | 74 | 输出完整性（漏键） |

### 7.3 归因与改进方向

错误归成三族：类别混淆（面料 / 图案 / 袖长）、小物件漏检（戒指 / 领饰）、输出完整性（漏键）。其中两条低成本方向已经实测过，都是负结果：

- 难例续训：在最终 adapter 上补难例续训，全 JSON 匹配率 44.4% < 45.8%、属性级准确率 92.6% < 93.4%——排除"难例数据不足"的假设
- 约束解码 / 后处理：可救回的全 JSON 匹配率样本 0 个——输出 JSON 可解析率已是 100%，没有格式层错误可修

因此剩余方向只剩解冻视觉塔或换更强视觉基座（细粒度判别的根因在视觉侧，数据侧与推理侧都够不着）。诊断过程、三条干预路线的配置与复跑见[错误分析](错误分析.md)。

## 10. 结论与展望

### 10.1 结论

1. 任务达成：LoRA 微调将服装属性抽取的属性级准确率从 59.8% 提升至 93.8%（+34.0pp），macro-F1 0.677，18 属性全部通过 McNemar 显著性检验，JSON 可解析率 100%——微调收益远超常见预期（细粒度任务上通用 VLM 的 0-shot 能力确实弱，领域微调空间巨大）；
2. 方法论价值：schema 感知指令在小模型上是决定性因素（8B 上 +31.5pp），数据效率高（5k 即达 92%），训练稳定无过拟合——这套"任务工程化 + 轻量微调 + 严谨评测"的组合可以迁移到其他结构化抽取场景（商品属性、证件信息、表格抽取等）。这条结论以 8B 为条件：换到 27B 后同一对照只剩 2.6pp，训练期指令从"决定性"退化为"加速项"，推理期的 schema prompt 仍是必需（边界与机制见 §6.4.4）；
3. 工程闭环完整：数据（防泄漏划分 + 质量关卡）→ 训练（LoRA + 口径一致）→ 评测（自建指标 + 统计检验 + 消融）→ 分析（badcase 归因）→ 部署（vLLM demo），可复现、可讲述；
4. 相似款检索（闭环落地）：在部署 demo 上落地相似款检索（图 → 属性 → 相似款），复用主线视觉塔抽 embedding + 官方属性约束加权，把抽取结果升级为完整的「电商标注 + 相似款检索」场景（详见 §8 与 [检索说明](检索说明.md)）。

### 10.2 局限

- 细粒度面料/图案准确率（88.6%）仍低于形状属性（96.3%），长尾类别（如 `furry`、`suspenders`）样本不足；
- 小物件（戒指、领饰）漏检率偏高；
- 全 JSON 匹配率 47.3% 仍有提升空间（任何单属性错误即判不匹配）。

### 10.3 展望

- 数据侧：针对混淆对补充困难样本、类别重加权；
- 模型侧：解冻视觉塔（对照实验）、约束解码保证输出 schema 合法性；
- 任务侧：扩展到多任务（属性 + 描述）、多部位细粒度分割辅助；
- 部署侧：vLLM 服务化 + 线上 A/B 验证真实电商货架属性收益。
