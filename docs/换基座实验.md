# 换基座实验

> 把主实验的基座从 Qwen3-VL-8B-Instruct（8.81B）换成 `models/Qwen3.8-27B`（27.36B），重跑全套主实验、两格消融与 checkpoint 快筛。
> 8B 的配置 / 权重 / 预测均未改动，27B 产物一律带 `_27b` 后缀独立存放。
>
> 结果一句话（test 集 4,410 条）：基座层面 27B 领先 23.1pt（82.9% vs 59.8%），微调后两者打平在 93~94%
> （93.7% vs 93.8%），但 27B 的 macro-F1 与全匹配率一致更好。换基座真正的收益是对训练期指令的鲁棒性——
> 同样 5k 数据，8B 从 schema 换 simple 掉 31.5pt，27B 只掉 2.6pt。
>
> 代码、配置与报告在 `experiments/qwen38_27b/`（各域入口见[实验索引](../experiments/README.md)），本文只讲决策、差异与结论。

## 1. 新基座

换基座的原因有两个：原主实验用的 Qwen3-VL-8B-Instruct 是上一代 8B 模型，需要跟上本族新一代；
同时要验证这套流水线（数据构造 / 训练 / 评测 / 报告）在换基座后是否仍然成立、结论是否随基座迁移。

`models/Qwen3.8-27B`（来源 ModelScope `Qwen/Qwen3.8-27B`，18 个 shard，约 54GB）：

| 项 | 值 |
|---|---|
| architectures / model_type | `Qwen3_5ForConditionalGeneration` / `qwen3_5` |
| 参数 | 27.36B（bf16 约 54GB） |
| 文本塔 | 64 层 / hidden 5120 / 24 heads / 4 KV heads / vocab 248320 |
| 视觉塔 | depth 27 / hidden 1152 / patch 16 / spatial_merge 2 |
| 架构特点 | 混合注意力：`full_attention_interval=4`，64 层里 48 层是 Gated DeltaNet 线性注意力，16 层是 full attention |
| 思考模式 | 默认开启（chat_template 未定义 `enable_thinking` 即视为 true） |

环境侧无需额外安装：transformers 5.8.0 已内置该模型类，LLaMA-Factory 0.9.6 已内置 `qwen3_5` 模板与复合模型注册。

## 2. 与 8B 主实验的四处差异

其余超参（lr / epoch / cutoff_len / LoRA rank·alpha·dropout / lora_target / 分辨率 / freeze 策略 / seed）逐字一致。

### 2.1 模板与思考开关

8B 用 `qwen3_vl_nothink`；27B 的正确「不思考」形式是 `qwen3_5` + `enable_thinking: false`。实测三种渲染：

| 配置 | prompt 尾部 | response |
|---|---|---|
| `qwen3_5` + `enable_thinking: false` | `assistant\n<think>\n\n</think>\n\n` | 纯 JSON |
| `qwen3_5` + `enable_thinking: true` | `assistant\n` | `<think>…</think>` + JSON |
| `qwen3_5_nothink` | `assistant\n` | 纯 JSON，但模型会自行生成 `<think>` |

`qwen3_5_nothink` 不是 `ReasoningTemplate`，而 `enable_thinking` 只在 `ReasoningTemplate` 上生效
（`vendor/llamafactory/src/llamafactory/data/template.py:700-709`），因此它不注入空 cot；冒烟实测用它时模型输出整段推理而非 JSON。

### 2.2 分布式改成 ZeRO-3

27B 的 bf16 权重约 54GB，超过单卡 48GB，DDP 每卡放不下完整副本，必须分片。新增 `experiments/qwen38_27b/main/config/ds_z3_27b.json`。

### 2.3 `use_reentrant_gc: false`

迁移里最难的一环：默认 reentrant 检查点 + ZeRO-3 时，加载后显存基线正常（19.2GB），但一进入训练就 OOM（47GB 打满）。
逐项排除后定位到根因——reentrant 检查点的 backward 重算路径绕过了 ZeRO-3 的参数释放逻辑，参数在 backward 期间无法回收。
改成非重入检查点（`use_reentrant_gc: false`）后显存立刻回落到健康区间。同时把 `contiguous_gradients` 设为 false。

### 2.4 等效 batch 保持 36

`per_device_train_batch_size: 4` × 3 卡 × `gradient_accumulation_steps: 3` = 36，与 8B 完全一致，可直接对比。

## 3. 与 8B 的一致性核对

对 7 个评测配置做了 8B 与 27B 的逐项键值 diff，差异全部集中在四类必要项，其余逐字一致：

| 差异类别 | 内容 | 是否影响可比性 |
|---|---|---|
| 基座 | `model_name_or_path` | 本次实验的自变量 |
| 思考开关 | `qwen3_vl_nothink` → `qwen3_5` + `enable_thinking: false` | 否（该模型族的等价 nothink 形式） |
| 分布式 | 新增 `deepspeed` / `use_reentrant_gc` | 否（只影响显存与并行方式） |
| 命名空间 | `output_dir` / `adapter_name_or_path` 加 `_27b` | 否（仅隔离产物） |

逐字保持一致的项：`eval_dataset`、`cutoff_len`、`max_samples`、`predict_with_generate`、`max_new_tokens`、
`do_sample`、`seed`、`image_max_pixels`、`quantization_method`。训练侧同样：`learning_rate`、`num_train_epochs`、
`cutoff_len`、LoRA 四参数、`lr_scheduler_type`、`warmup_steps`、`save_steps`、`eval_steps`、`val_size`、`seed`、
两个 freeze 开关、`image_max_pixels`。

> 说明：27B 实际由 `experiments/qwen38_27b/main/scripts/infer_27b.py` 执行，配置里的 `deepspeed` / `predict_with_generate` / `per_device_eval_batch_size`
> 对它是无效键；保留它们是为了让「与 8B 配置逐字对比」这件事本身可核对。真正生效的等价项是
> `eval_dataset`、`cutoff_len`、`max_new_tokens`、`do_sample`、`seed`、`image_max_pixels`、`template`（+ `enable_thinking`）。

## 4. 实验结果

本章与主文档 §6 同构：先给主结果与品类分层，再讲归因（消融），然后是适用边界，最后是训练过程、成本与汇总。全部变体均为全量 4,410 条。

### 4.1 实验设计

两个基座 × 两个模型状态，在同一份数据与评测口径下各跑一遍；8B 用主实验已有的结果，27B 全部重跑：

| 对照 | 8B | 27B | 唯一变量 |
|---|---|---|---|
| Base 0-shot（val / test） | 主实验已有 | 重跑 | 基座 |
| LoRA 全量微调（val / test） | 主实验已有 | 重跑 | 基座 |
| 推理期换 simple 指令 · LoRA（val） | 主实验已有 | 重跑 | 推理指令 |
| 推理期换 simple 指令 · Base（val） | 未测 | 补测 | 推理指令 |
| Base 2-shot（val） | 主实验已有 | 重跑 | 示例数 |
| 压缩分辨率 589,824（val） | 主实验已有 | 重跑 | 评测分辨率 |
| 品类分层（test LoRA） | 主实验已有 | 重跑 | —（同一模型换切面） |
| 指令范式 × 数据量（5k 两格） | 主实验已有 | 重跑 | 训练指令 |
| checkpoint 快筛（15 点） | 主实验已有 | 重跑 | 训练步数 |

### 4.2 主结果

#### 4.2.1 主结果

每个变体全量 4,410 条，下表为 test 集（val 上的差异同向，见 §4.3 的消融）。

| 指标 | 8B | 27B | Δ |
|---|---|---|---|
| 属性级准确率 · Base 0-shot | 59.8% | 82.9% | +23.1pt |
| 属性级准确率 · LoRA | 93.8% | 93.7% | −0.1pt |
| 全 JSON 匹配率 · Base 0-shot | 0.0% | 1.8% | +1.8pt |
| 全 JSON 匹配率 · LoRA | 47.3% | 49.6% | +2.3pt |
| macro-F1 · Base 0-shot | 0.417 | 0.521 | +0.104 |
| macro-F1 · LoRA | 0.677 | 0.682 | +0.005 |

两个状态给出两件事。基座层面 27B 三个指标全面领先：准确率 +23.1pt、全匹配从 0% 变成 1.8%、macro-F1 +0.104。微调后准确率打平（−0.1pt），但严格口径仍是 27B 好——全匹配 +2.3pt、macro-F1 +0.005，即 27B 更容易一次输出整段正确的 JSON。两侧 JSON 可解析率均为 100.0%。

逐属性 McNemar：27B 的 Base→LoRA 提升在 18 个属性上全部 p<0.05（test 总体 b=7285、c=1223，χ²=4317.79，p<0.001）。

#### 4.2.2 品类分层

| 口径（test LoRA） | 8B | 27B |
|---|---|---|
| 全部品类准确率 | 93.8% | 94.8% |
| 品类区间 | 90.1%~100.0% | 90.8%~100.0% |
| 性别（MEN / WOMEN） | 96.6% / 94.6% | 96.9% / 94.6% |

27B 高 1pt，两者都无灾难性品类；性别维度几乎相同（27B 只高 0.3pt），说明那 1pt 的差距主要来自品类间的均衡度而非某一群体。

### 4.3 提升归因

#### 4.3.1 指令范式与数据量

8B 的五格消融里 `schema-35k` 就是主实验本身，其余四格全量重跑约需 125 GPU 小时；27B 只补信息量最大的两格
（`schema-5k` 与 `simple-5k`），都在 val 全量 4,410 条上评测：

| 格子 | 8B 准确率 | 27B 准确率 | Δ |
|---|---|---|---|
| simple-5k | 60.4% | 89.5% | +29.1pt |
| schema-5k | 91.9% | 92.0% | +0.1pt |
| schema-35k（主实验） | 93.4% | 93.4% | −0.0pt |

相邻两行各构成一组对照：`simple-5k` 与 `schema-5k` 同数据量、只改训练指令，`schema-5k` 与 `schema-35k` 同指令、只改数据量。
严格口径上 27B 在两个 schema 格都更好：macro-F1 +0.016 / +0.008，全匹配率 +3.0pt / +3.6pt。

三条结论：

- 数据量曲线与基座规模无关：schema 分支 5k→35k（7 倍数据）只涨 1.4pt，8B 同区间 1.5pt，两个端点与 8B 同格相差 ≤0.1pt
- 换基座最大的实际收益在指令鲁棒性：同样是 5k、唯一变量是训练期指令，8B 从 schema 换 simple 掉 31.5pt，27B 只掉 2.6pt
- 这个差距的来源不是「27B 判得更准」，而是「27B 记得住整套键」，见 §4.3.2

不再补 20k 与 simple-35k 的理由：27B 的 schema 曲线两端已与 8B 重合，8B 已知的 20k=92.9% 也落在同一条线上；
simple-35k 同理——8B 加到 7 倍数据也只从 60.4% 升到 75.3%，始终够不到 schema 分支。详见
[ablation/README.md](../experiments/qwen38_27b/ablation/README.md) 与 `experiments/qwen38_27b/ablation/reports/report_ablation_27b.md`。

#### 4.3.2 simple-5k 在 27B 上为何不塌

抽查两套预测各 1,200 条：差别几乎全部集中在「缺键」这一个指标上，即真值里有、模型没输出的键，
按评测口径一律算错。

| 配置 | 平均缺键数 / 条 | 属性级准确率 |
|---|---|---|
| 8B simple-5k | 4.13 | 60.4% |
| 8B simple-20k | 2.41 | 74.0% |
| 8B simple-35k | 1.85 | 75.3% |
| 8B schema-5k | 0.19 | 91.9% |
| 27B simple-5k | 0.14 | 89.5% |
| 27B schema-5k | 0.24 | 92.0% |

8B 的漏键集中在低频属性：`upper_clothing_covering_navel` 0.0%（1,200 条漏 852）、`neckwear` 2.6%（漏 1,020）、
`outer_clothing_is_cardigan` 5.7%（漏 765）、`wrist_wearing` 28.1%、`ring` 28.5%。平均每条漏 4.13 个键，
约占可见属性总量的三分之一，准确率上限因此被压到 68% 左右。

27B 只漏 0.14 个键，剩余误差是真实的视觉难例，形态与 schema-5k 一致：`outer_fabric` 71.6%、
`upper_pattern` 76.9%、`neckline` 78.1%，而 `glasses` / `hat` 在 99% 以上。它的全匹配率仍只有 3.9%
（schema-5k 为 40.8%），是因为低频键偶尔漏一两个，而不是键名错乱——1,200 条里只有 4 次非官方键名。

这组数字改变了「schema 指令」的作用表述：对 8B 来说，它的首要作用不是告诉模型每个键有哪些取值，
而是告诉它一共有哪些键。8B 的 simple 曲线（缺键 4.13 → 2.41 → 1.85）本质是在用数据量补这份输出空间知识，
加到 7 倍数据仍比 schema-5k 差约 10 倍，所以追不上；27B 用 5k 就把这件事做完了。

> 这是从两套预测文件反推的事后分析，不是设计的对照实验。要严格验证「漏键假说」，可以把 8B simple-5k
> 的预测按真值补齐缺失键后重新打分，看准确率回升多少。


### 4.4 适用边界

#### 4.4.1 推理期指令

| 模型 × 推理指令 | 8B | 27B |
|---|---|---|
| LoRA + schema prompt（与训练一致） | 93.4% | 93.4% |
| LoRA + simple prompt | 0.2% | 0.4% |
| Δ | −93.2pt | −93.0pt |

两边都塌到 0.2% / 0.4%：JSON 可解析率仍有 99.7% / 99.7%，但输出不再按 18 维键名对齐。行为一致——推理期的 schema prompt 是硬性前提。

#### 4.4.2 few-shot 对照

| 模型 × 示例数 | 8B | 27B |
|---|---|---|
| Base 0-shot（schema 指令） | 59.9% | 82.6% |
| Base 2-shot（schema + 2 示例） | 72.3% | 80.8% |
| Δ（0-shot → 2-shot） | +12.4pt | −1.7pt |

8B 靠示例补能力（+12.4pt），27B 基座已经足够强，加示例反而略降（−1.7pt）。这是两组对照里行为不同的一处。

#### 4.4.3 图像分辨率

| 模型 × 评测输入 | 8B LoRA | 27B LoRA |
|---|---|---|
| 825,750（不压缩，与训练一致） | 93.4% | 93.4% |
| 589,824（压缩） | 93.0% | 93.0% |
| Δ | −0.4pt | −0.4pt |

两边的损失完全相同（各 −0.4pt），macro-F1 也都不掉。行为一致——分辨率不是敏感因素。

#### 4.4.4 推理侧指令矩阵

这一格是 27B 补测的：8B 主实验只有「LoRA + simple 指令」，没有「基座 + simple 指令」——8B 的 simple 对照都是训练期用 simple 数据训出来的模型，基座本身没配 simple prompt 评过。所以下表只做 27B 内部诊断，不构成跨基座对比。

| 模型（27B） | schema 指令 | simple 指令 |
|---|---|---|
| Base 0-shot | 82.6% | 0.1%（JSON 可解析率 99.8%） |
| LoRA | 93.4% | 0.4%（JSON 可解析率 99.7%） |

补这一格是为了回答「指令依赖是不是微调造成的」。答案是：基座在 simple 指令下同样崩到 0.1%，说明这是模型固有行为，不是 schema 过拟合。
「推理期必须携带 schema prompt」这条结论在微调前后都成立。见 `experiments/qwen38_27b/main/reports/report_supplement_27b.md`。


边界小结：推理期指令与图像分辨率两组一致，few-shot 与品类均衡度两处不同——前者说明 27B 同样离不开 schema prompt、也同样是分辨率不敏感，后者说明它已经越过「靠示例补差」的阶段。

### 4.5 训练过程

| 训练步数 | 准确率 | macro-F1 | 全匹配 |
|---|---|---|---|
| 100 | 92.1% | 0.676 | 33.0% |
| 900 | 93.5% | 0.657 | 46.2% |
| 2100（屏幕最优） | 93.7% | 0.669 | 52.0% |
| 2793（主实验所用） | 93.5% | 0.650 | 52.0% |

27B 极早饱和：第 100 步（全部训练的 3.6%）已有 92.1%，900 步（32%）到 93.5%，此后 1900 步只再动 ±0.2pt。
含义是那 49 小时里约 2/3 是冗余的，若重跑可 `save_steps=900` 早停。口径提醒：500 条样本下 0.2pt 属噪声；
8B 当年对 900 / 2100 做过 4410 条全量确认，27B 尚未做。详见 [ckpt_screen/README.md](../experiments/qwen38_27b/ckpt_screen/README.md)。

训练样本 token 长度实测 min 1170 / p50 1268 / max 1316，无一条超过 `cutoff_len=2048`，因此 batch=4 的显存峰值可预测。

### 4.7 实验汇总

| 维度 | 实验 | 唯一变量 | 结论 |
|---|---|---|---|
| 基座能力 | 主结果（test） | 是否换基座 | 27B 82.9% vs 8B 59.8%，+23.1pt |
| 微调后水平 | 主结果（test） | 是否换基座 | 93.7% vs 93.8%，打平 |
| 严格口径 | 主结果（test） | 是否换基座 | 全 JSON 匹配率 +2.3pt、macro-F1 +0.005，27B 一致更好 |
| 训练期指令鲁棒性 | 消融（5k 两格） | 训练指令 | 8B 掉 31.5pp vs 27B 掉 2.6pp |
| 数据效率 | 消融（schema 5k→35k） | 数据量 | +1.4pt（8B 同区间 +1.5pt，曲线重合） |
| 收敛速度 | checkpoint 快筛 | 训练步数 | 100 步即 92.1%，900 步到 93.5% |
| 成本 | 训练与推理实测 | 基座规模 | 训练 49h（8B 9.9h）、显存 46GB/卡（8B 30GB） |

一句话：3 倍参数、5 倍训练时间，换来基座能力 +23pt、微调后打平、严格口径小胜，以及训练期指令鲁棒性的质变——后者是这次换基座最有信息量的产出。


### 4.8 结论

1. 基座层面 27B 全面胜出：准确率 +22.7pt（val）/ +23.1pt（test），全匹配率从 0% 升到 1.4~1.8%。
2. 微调后两者基本打平在 93~94%：准确率差 ≤0.1pt，但 27B 在更严格口径上一致更好——macro-F1 两个 split 均 +0.005~0.008，全匹配率 +2.3~3.6pt。
3. 因此这个任务的瓶颈在数据与标注口径，而不是模型容量：8B 已接近该口径的天花板，27B 的价值体现在基座泛化和「整条 JSON 全对」的一致性上。2-shot 对照是佐证——27B 不需要靠 in-context 示例补能力。


## 5. 复现

环境：`/home/maotai/.conda/envs/lf`；训练前需 `export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。

```bash
# 训练（约 49 小时，tmux 常驻）
tmux new-session -d -s train27b "bash experiments/qwen38_27b/main/scripts/run_train_27b.sh"
```

## 6. 未采用方案与未跑项

已评估但未采用：

- vLLM 0.27.1 确实注册了 `Qwen3_5ForConditionalGeneration`，但它走模型自带 jinja 模板，与 LF 的 `qwen3_5`
  在图像 token 注入方式上不同，需要额外的 token-id 对齐验证；为稳妥先用 transformers 方案
- transformers 原生 TP：`Qwen3_5Config.base_model_tp_plan` 与 `Qwen3_5ForConditionalGeneration._tp_plan` 均为 `None`，不可用
- ZeRO-3 推理：单 token 解码受参数 all-gather 带宽限制，不可行

未跑的项目与理由：

- 20k / simple-35k 两个消融格：见 §4.3.1（曲线已由两个基座验证）
- 27B 的 900 / 2100 全量确认：500 条快筛已足够给出「早饱和」判断，全量确认只影响 0.2pt 噪声内的排序
- 27B 的 badcase 实验：8B 上已实证两条低成本路线为负（难例续训 44.4%<45.8%、约束解码救回 0），
  27B 的剩余错误同样是视觉本质难例，重跑预期不改变结论
